# Editorial workflow (isolated V2 candidate)

The public site is still generated by `build_pages.py`. Visitors never query PostgreSQL. `editorial/migrations/001_initial.sql` targets a Supabase PostgreSQL project; it has not been applied to a real project yet.

## Data and access

An article has one stable shared slug and up to three independently publishable translations. Categories and tags are separate tables. Revision snapshots and publication events are retained. Media uploads begin in a private Storage bucket and record their rights status. The exporter deliberately omits cover images until a separately reviewed public-media flow exists.

RLS permits anonymous reads only for translations with `status=published` and `published_at` in the past. Anonymous writes have no policy or grant. An authenticated user can edit only if their `auth.users.id` is manually enrolled in `editorial_private.admins`. Signup must be disabled in Supabase Auth; no registration UI is provided. Publication changes are logged by a database trigger, and published text must be withdrawn before editing. No service-role or secret key is used in browser code.

## Setup in a private Supabase project

1. Create the project, disable public signup, enable the desired MFA policy, and verify the admin account.
2. Apply `migrations/001_initial.sql` in the SQL editor. This migration requires Supabase `auth` and `storage` schemas and cannot be tested with plain PostgreSQL alone.
3. Enroll only the verified administrator using `INSERT INTO editorial_private.admins(user_id) VALUES ('<verified-auth-user-uuid>');` in the private SQL editor. Do not commit that UUID or credential.
4. Test that the publishable key alone can read only published rows and cannot write; test that a signed-in non-admin cannot write; test the admin's draft, revision, media and publication flows before deployment.
5. Configure `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` as protected build settings, then build the isolated admin preview: `python3 editorial/build_admin.py --output /tmp/portfolio-editorial-admin-preview`. The generated `config.json` contains only a publishable key, never a secret key. Do not copy this preview into the public site's `public/` directory.

The admin UI is in `editorial/admin/` and uses Supabase Auth plus the database's RLS policies. The access token stays in memory and is cleared on sign-out; reloading requires another sign-in. The preview renders article text with `textContent`, so raw HTML is not interpreted. Images upload only to the private bucket with pending rights. The UI and migration still need live integration tests against the configured Supabase project.

## Approved static publication

`export_public.py` fetches only RLS-visible public translations with the publishable key. It can also accept a local JSON fixture. It writes a **new staging directory outside the repository**, never `content/` or `public/` directly:

```sh
python3 editorial/export_public.py --fixture /path/to/reviewed-fixture.json --output /tmp/editorial-stage-new
```

Review `articles.json` and all generated fragments, then copy approved files to `content/articles.json` and `content/articles/<slug>/<language>.html` in a reviewed Git change. Run `build_pages.py`, `check_site.py` and the release tests. No automatic cross-posting, database-triggered deployment or timed publication is enabled. `scheduled_at` stores editorial intent; a future approved scheduler would still need to update status and trigger a new static build.

The exporter uses a deliberately small Markdown subset and escapes all input, including raw HTML. It never exports drafts, future-dated translations or private media. Confirm rights and metadata for any article or image before publication.
